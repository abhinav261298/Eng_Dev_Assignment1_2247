Delivery Failure Root-Cause Analysis — POC Solution

Goal: aggregate the fragmented logistics data sources (orders, fleet logs, warehouse logs, external conditions, customer feedback), correlate events across them, and generate human-readable, evidence-grounded explanations and recommendations for delivery failures and delays — answering questions such as "Why were deliveries delayed in city X yesterday?" without manual cross-system investigation.

1. Solution Overview

The POC is a lightweight, fully local TypeScript/Node.js + SQLite application:

sample-data-set/*.csv  (8 provided files — read-only)
        |
        |  src/ingest.ts   csv-parse, type coercion, 17-check data-quality report
        v
  logistics.db  (SQLite)
        |  schema.sql: 8 base tables + 10 indexes + 8 views
        |  (v_order_outcome, v_order_fleet, v_order_warehouse, v_order_external,
        |   v_order_feedback, order_360, v_order_warehouse_pairs, v_order_driver_pairs)
        v
  src/insights/*   deterministic engine: UC1-UC6
        |           filter -> outcome split -> recorded causes -> corroboration
        |           -> association lifts vs baseline -> evidence JSON
        v
  src/narrative/*  OpenAI renderer (optional, strictly grounded in the evidence JSON)
        |           -> deterministic template renderer as guaranteed fallback
        v
  src/cli.ts       menu of the six use cases, parameter validation against DB values,
                   every answer saved as JSON (evidence) + TXT (narrative)

Design principle: every number in every narrative is computed by the deterministic SQL/TypeScript engine. The optional LLM layer only rewrites the computed evidence into prose and is forbidden from calculating or inventing facts; if it is unavailable or fails, a deterministic template produces the same content. The six use cases therefore never depend on LLM availability.

3. Correlation Methodology — Three Evidence Tiers

The engine never claims causality it cannot support. Every fact in an answer belongs to one of three tiers, and the narrative language is constrained per tier (enforced in the template renderer and in the LLM prompt):

TierSourceLanguage allowed
1. Recorded causeorders.failure_reason — present on 100% of failed ordersCausal: "failed due to Stockout"
2. CorroborationPer-order cross-check of the recorded reason against matching log evidence (e.g. "Incorrect address" × fleet "Address not found" note)"corroborated by ... in N/M orders"
3. AssociationRate of an evidence flag in the population vs a stated baseline (lift), surfaced only with support n ≥ 30"associated with / co-occurred with" — never causal

Honesty note: the provided synthetic dataset shows weak cross-table correlations (association lifts are typically a few percentage points). The engine reports weak signals as weak instead of manufacturing narratives — the recorded failure reason plus its corroboration rate is the reliable core of every answer, and every answer ends with explicit caveats.

4. How Each Use Case Is Answered

#QuestionEngine logic (over the order_360 view)
1Why were deliveries delayed in city X on day D?Orders due (promised date = D) in X → outcome split → recorded reasons for failures + corroboration → association lifts vs the city's own baseline. Late-but-delivered orders have no recorded reason; they rely on tier-3 evidence only (stated in the answer).
2Why did client C's orders fail in a window?C's orders in window → reason ranking + corroboration → window failure rate vs C's all-time rate vs system rate.
3Top failure reasons linked to warehouse W in month M?Pair-level: all orders W touched in M → reason ranking → W's picking/dispatch durations vs all-warehouse averages → W's city mix shown for confounder visibility.
4Compare failure causes: city A vs city B in month M?Symmetric per-city blocks (volume, failure/late rates, reason mix, lifts vs all-city baseline) + failure-rate gap.
5Likely causes during the festival period; how to prepare?Festival-flagged orders vs non-festival baseline → rate deltas + reason mix → preparation recommendations keyed to the top recorded reasons.
6Risks of onboarding ~20,000 extra monthly orders?Explicit projection: historical failure/late rates by reason scaled to the new volume; capacity context per target city (warehouse capacity totals, active drivers); mitigations keyed to the largest projected reasons.

5. Architecture Options Considered

OptionSummaryAssessment
A. In-memory dataframe pipelineLoad CSVs, join and aggregate in codeFastest to build, but join/dedup rules end up buried in code; fan-out mistakes are easy
B. SQLite + typed engine (chosen)Schema + views encode the data model once; use cases are parameterized queries + narrative templatesExplicit, verifiable data model; ad-hoc questions become SQL; zero infrastructure
C. LLM-centric analysisLLM interprets questions and writes narratives directly over dataRejected as the core: non-deterministic, can hallucinate correlations the data does not contain

The chosen design uses C's idea only as a thin optional layer on top of B: the LLM (OpenAI, key via .env) rewrites the deterministic evidence JSON into prose under strict rules, with the template renderer as a guaranteed fallback.

8. Limitations & Future Enhancements

  • Natural-language question parsing is out of POC scope by decision; the CLI offers the six predefined use cases with validated parameters. A future LLM intent-parser can map free-form questions onto the same engine.
  • Association analysis reports co-occurrence lifts, not causal inference; with production-grade data (coherent timestamps, richer factors) regression or uplift modeling could be added.
  • Warehouse capacity units are not defined in the data and are reported as-is.
  • The LLM layer was verified with mocked clients and by fallback behavior; live-key usage is optional and never required for the demo.
